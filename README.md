# Scanner API

Бэкенд для мобильного приложения сканера билетов. Работает с общей базой Sxodim/ShowGo.

## Стек

- Python 3.14, FastAPI, SQLAlchemy 2.0 (async), asyncpg
- PostgreSQL (удалённая БД через SSL)
- JWT-авторизация (PyJWT + bcrypt)

## Быстрый старт

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Скопировать `.env.example` → `.env` и заполнить доступы к БД.

```bash
python run.py
```

Сервер поднимется на `http://localhost:5001`. Swagger — `/docs`.

## Переменные окружения

| Переменная | Описание |
|---|---|
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Подключение к PostgreSQL |
| `DB_PGBOUNCER` | `true`, если перед БД стоит pgbouncer в transaction-режиме (KZ). Отключает кэши prepared statements и включает уникальные имена для них. Для прямого подключения к Postgres — `false` (по умолчанию) |
| `DB_POOL_SIZE` | Размер пула соединений (по умолчанию `10`) |
| `DB_MAX_OVERFLOW` | Сколько соединений можно открыть сверх пула (по умолчанию `10`). Потолок от сервиса = `DB_POOL_SIZE + DB_MAX_OVERFLOW`; сверять с `max_client_conn` у pgbouncer либо с `max_connections` у Postgres |
| `SECRET_KEY` | Ключ для подписи JWT |
| `ACCESS_TOKEN_EXPIRE_DAYS` | Срок жизни токена (дни) |
| `DEFAULT_COUNTRY_CODE` | Код страны по умолчанию (`uz`) |
| `TIME_ZONE_DIFFERENCE` | Разница с UTC в часах |
| `SCAN_ZONE_COLUMNS` | `true` — после добавления в базу колонок `user_permissions.scan_zone` и `scan_logs.payload` (см. «Зоны сканирования»). По умолчанию `false`: сервис к этим колонкам не обращается. Если включить, а колонок нет, сервис при старте пишет ошибку в лог и работает как при `false` |
| `COUNTS_CACHE_TTL` | Сколько секунд счётчики сеанса живут в памяти процесса (по умолчанию `3`, `0` — считать на каждый скан) |
| `AUTH_CACHE_TTL` | Сколько секунд учётка контролёра живёт в памяти процесса (по умолчанию `30`, `0` — читать на каждый запрос). Правка прав или зоны в админке доходит до сканера с этой задержкой |

## API

`POST /api/v1/auth/` — логин, возвращает JWT с `permission_id`

Все остальные эндпоинты требуют `Authorization: Bearer <token>`:

- `GET /api/v1/event/list` — список сессий на сегодня
- `POST /api/v1/check` — сканирование билета (вход/выход)
- `GET /api/v1/ticket/list/{session_id}` — список билетов сессии
- `GET /api/v1/ticket/search/{session_id}/{ticket_number}` — поиск по номеру
- `GET /api/v1/ticket/search/by_mail/{session_id}/{email}` — поиск по email
- `GET /api/v1/statistics/{session_id}` — статистика продаж/сканирований
- `GET /api/v1/zone/statistic/{session_id}` — статистика сеанса по зонам: сколько пришло и сколько осталось; из этих же строк собирается зона

## Зоны сканирования

Зона — фильтр билетов, которые пропускает сканер. Отдельных таблиц нет: зона собирается из типов билетов, областей схемы и секторов сеанса.

```json
{
  "title": "Фан-зона",
  "session_ids": [4591],
  "all_seats": false,
  "sectors": ["A", "B"],
  "all_entry": false,
  "type_ids": [1613, 1614],
  "area_ids": [],
  "option_ids": []
}
```

| Поле | Что пропускает |
|---|---|
| `all_seats` | все билеты с местом |
| `sectors` | билеты с местом в этих секторах (`ticket_seats.sector` — то, что напечатано на билете после слова «Сектор»); пустая строка `""` — места без сектора |
| `all_entry` | все входные билеты (без места) |
| `type_ids` | входные билеты этих типов (`ticket_types.id`) |
| `area_ids` | входные билеты этих областей схемы (`ticket_areas.id`) |
| `option_ids` | доп. опции сеанса, например Fast Track (`session_options.id`). Опция — не билет: правила для билетов, включая `all_entry`, её не пропускают |
| `session_ids` | сеансы, на которых зона действует; пусто — на всех |

Билет подходит, если сработало хотя бы одно правило. Зона без правил ничего не ограничивает.

Откуда берётся зона:

1. **Из учётки контролёра** — `user_permissions.scan_zone`, задаётся в админке. Пока она действует на сеансе, выбор приложения не учитывается; `/event/list` и `/zone/statistic` отдают её с `zone_locked: true`, и приложение выбор не показывает.
2. **Из приложения** — если зона за учёткой не закреплена, контролёр отмечает нужное по данным `/zone/statistic/{session_id}`, а приложение шлёт выбор в `data.zone` запроса `/check`.
3. Зоны нет нигде — сканер работает как раньше, без ограничения.

Билет из другой зоны не гасится. Ответ `/check`: `status: "error_invalid"`, `message: "ДРУГАЯ ЗОНА"`, `error_code: "wrong_zone"`. Статус оставлен прежним, чтобы старые версии приложения показывали отказ без обновления. Счётчики в ответах считаются по билетам зоны.

Колонки в общей базе (схему ведёт `showgo_api`, выполнить до включения `SCAN_ZONE_COLUMNS`):

```sql
SET lock_timeout = '3s';
ALTER TABLE user_permissions ADD COLUMN IF NOT EXISTS scan_zone jsonb;
ALTER TABLE scan_logs ADD COLUMN IF NOT EXISTS payload jsonb;
```

Индекс для истории сканирований билета (вне транзакции):

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_scan_logs_order_item_id ON scan_logs (order_item_id);
```

## Вход в приложение и состав базы

Правка сотрудника в админке не выкидывает его из приложения. Админка при правке удаляет права и создаёт заново, id права в токене устаревает — сервис тогда берёт действующее право сканера этого пользователя, как при новом входе. Новая зона или область доступа доходят за `AUTH_CACHE_TTL` секунд. Если доступ к сканеру сняли, запросы получают 403.

Смена пароля выкидывает: вход, выданный до `users.password_changed_at`, получает 401 `password_changed`. Токены без времени выдачи (выданные до этой версии) считаются старыми только у тех, кто пароль менял.

Схему базы ведёт `showgo_api`, и у стран она разная. При старте сервис сам смотрит, что есть, и к отсутствующему не обращается:

| Чего нет в базе | Как работает сервис |
|---|---|
| `users.password_changed_at` | смена пароля из приложения не выкидывает |
| `order_items.session_option_id`, `session_options` | доп. опций нет, `options` в статистике пустой |
| `user_permissions.scan_zone`, `scan_logs.payload` | как при `SCAN_ZONE_COLUMNS=false` |

После добавления колонок сервис нужно перезапустить.

## Статистика по зонам

`GET /api/v1/zone/statistic/{session_id}` возвращает счётчики по действующим билетам сеанса:

| Блок | Что в нём |
|---|---|
| `total` | весь сеанс |
| `zones` | зоны, назначенные контролёрам в админке (по названию зоны); нужен `SCAN_ZONE_COLUMNS=true` |
| `sectors` | билеты с местом — по секторам; места без сектора идут последней строкой (`sector: ""`, `title: "Без сектора"`) |
| `types` | билеты без места — по типам билетов (сеанс без схемы): «Фан-зона», «Танцпол» |
| `areas` | билеты без места — по областям схемы (стоячие зоны, нарисованные на схеме зала) |
| `seats`, `entry` | итог по всем сидячим и по всем входным |
| `options` | доп. опции сеанса (Fast Track и т.п.) — каждая отдельной строкой |

Билет с местом считается только в своём секторе, билет без места — только в своём типе или области, поэтому строки не пересекаются: сумма `sectors` равна `seats`. Строки есть всегда, назначены зоны контролёрам или нет.

Доп. опции — не билеты: в `total`, `entry` и в счётчики сеанса (`/event/list`, `/check` без зоны) они не входят, скан опции эти счётчики не меняет. Сколько опций отсканировано и сколько осталось — в `options`.

В каждой строке: `all_count` — всего билетов, `scan_count` — пришли, `in_count` — сейчас внутри, `out_count` — вышли, `left_count` — ещё не пришли. Ответ держится в памяти `COUNTS_CACHE_TTL` секунд.

## Журнал сканирований

Каждый скан билета пишется в `scan_logs`: кто (`user_id`), когда (`date_scan`), какой билет (`order_item_id`) и тип (`type_scan`). `IN` и `OUT` — проходы, `IN_ERROR` и `OUT_ERROR` — попытки, которые проходом не закончились.

При `SCAN_ZONE_COLUMNS=true` подробности попытки сохраняются в `scan_logs.payload` (JSON):

| Ключ | Значение |
|---|---|
| `result` | исход (см. ниже) |
| `session_id` | сеанс, открытый в сканере |
| `zone` | зона, по которой шла проверка |
| `zone_source` | `account` — зона из учётки, `app` — выбрана в приложении |

Новые сведения добавляются в `payload` без миграций.

| `result` | Подпись в истории | Когда |
|---|---|---|
| `allowed` | Вход / Выход | проход разрешён |
| `already_used` | Повторный вход / Повторный выход | билет уже отмечен |
| `wrong_event` | Другое мероприятие | билет другого сеанса |
| `ticket_refund` | Билет отменен (возврат) | билет возвращён |
| `order_cancelled` | Заказ отменен | заказ отменён |
| `order_refund` | Заказ возвращен | заказ возвращён |
| `order_failed` | Ошибка оплаты | заказ не оплачен |
| `wrong_zone` | Другая зона | билет из другой зоны |

Без колонки `payload` в журнал пишутся только проходы и повторы: причину остальных отказов хранить негде.

Ответ `/check` несёт историю билета:

- `scan_logs` — прежние сканы; у каждого `result`, готовая подпись `message`, время и имя контролёра;
- `attempts` — сколько раз билет сканировали до этого: `total`, из них `passed` (проходы) и `rejected` (отказы).

Несуществующий билет в журнал не попадает (записи привязаны к билету) — такие запросы видны только в логах сервиса.
